[PDF_BLOCK b1]

[PDF_BLOCK b2]
Providing Persistent Storage for Program Objects

[PDF_BLOCK b3]
In a file system, the values of program variables or objects are discarded
once a program terminates

[PDF_BLOCK b4]
When the need arises to read this data once more, the programmer
must convert from the file format to the program variable or object
structure.

[PDF_BLOCK b5]
DBMS software automatically performs any necessary conversions.

[PDF_BLOCK b6]
Such an object is said to be persistent since it survives the termination
of program execution and can later be directly retrieved by another
program.

[PDF_BLOCK b1]
File System vs. DBMS

[PDF_BLOCK b2]
Providing [REDACTED: PERSON_NAME] and Search Techniques for Efficient
Query Processing

[PDF_BLOCK b3]
Database systems must provide capabilities for efficiently executing
queries and updates.

[PDF_BLOCK b4]
Because the database is typically stored on disk, the DBMS must
provide specialized data structures (indexes) and search techniques to
speed up disk search for the desired records.

[PDF_BLOCK b5]
In order to process the database records needed by a particular query,
those records must be copied from disk to main memory.

[PDF_BLOCK b6]
Therefore, the DBMS often has a buffering or caching module that
maintains parts of the database in main memory buffers.

[PDF_BLOCK b7]
The query processing and optimization module of the DBMS is respon-
sible for choosing an efficient query execution plan for each query based
on the existing storage structures.

5 Sharing of data and multi-user transaction processing
Allowing a set of concurrent users to retrieve from and to update the
database.
Concurrency control within the DBMS guarantees that each transac-
tion is correctly executed or aborted.
Recovery subsystem ensures each completed transaction has its effect
permanently recorded in the database.
OLTP (Online Transaction Processing) is a major part of database
applications. This allows hundreds of concurrent transactions to execute
per second.

Data redundancy may lead to data inconsistency and higher storage
costs.
The same information may be replicated in several files in the file pro-
cessing approach.
For example, any changes to the records of one file will not affect the
records of other files.

8 Integrity Problem
The data stored in the database must satisfy certain types of

Hard to add new constraints or change existing ones in the case of a

Uncontrolled concurrent accesses can lead to inconsistencies.

[PDF_BLOCK b2]
11 Atomicity Problem
A computer system, like any other device, is subject to failure.
In many applications, it is crucial that, if a failure occurs, the data be
restored to the consistent state that existed prior to the failure.
All the operations in a database must be atomic Either the operation
is entirely executed or None of the steps of the operation should be
executed.
It is difficult to ensure atomicity in a conventional file processing system

[PDF_BLOCK b2]
External/ View level

[PDF_BLOCK b3]
Describes only part of the database that a particular user group is
interested in and hides the rest of the database from that group.

[PDF_BLOCK b4]
External schemas describe various user views

[PDF_BLOCK b5]
Simplifies the end user’s interaction with the system

[PDF_BLOCK b6]
System may produce many views for the same database

[PDF_BLOCK b7]
Conceptual / Logical level

[PDF_BLOCK b8]
Hides the details of physical storage structures and concentrates on
describing entities, data types, relationships, user operations, and
constraints

[PDF_BLOCK b9]
Describes what data are stored in the database and what relationships
exist among those data

[PDF_BLOCK b10]
Conceptual schema describes the structure and constraints of the
whole database

Three-Schema Architecture

[PDF_BLOCK b2]
DBMS must transform a request specified on an external schema
(user level) into a request against the conceptual schema, and then
into a request on the internal schema for processing over the stored
database.

[PDF_BLOCK b3]
➔Programs refer to an external schema and are mapped by the DBMS to

[PDF_BLOCK b4]
the internal schema for execution.
➔Data extracted from the internal DBMS level is reformatted to match

[PDF_BLOCK b5]
the user’s external view (e.g., formatting the results of an SQL query
for the display on a Web page)

[PDF_BLOCK b6]
If the request is a database retrieval, the data extracted from the
stored database must be reformatted to match the user’s external
view.

[PDF_BLOCK b7]
The processes of transforming requests and results between levels are
called mappings.

[PDF_BLOCK b1]
Data Independence

[PDF_BLOCK b2]
Defined as the capacity to change the schema at one level of a
database system without having to change the schema at the next
higher level.

[PDF_BLOCK b3]
Catalog includes information on how to map requests and data
among the various levels.

[PDF_BLOCK b4]
When a schema at a lower level is changed, only the mappings
between this schema and higher-level schemas need to be changed in
a DBMS that fully supports data independence.

[PDF_BLOCK b5]
The higher-level schemas themselves are unchanged. Hence, the
application programs referring to the higher-level schemas need not
be changed.
